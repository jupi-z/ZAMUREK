## Synthèse

- **Architecture directrice cohérente** : API NestJS modulaire, registry central, base PostgreSQL dédiée par boutique, Android React UI + Kotlin Core via Capacitor, canaux personnalisés compatibles avec future marketplace.
- **Risque principal non technique** : multiplication d'applications très ressemblantes sur Google Play, qui peut être considérée comme « repetitive content » (documentation officielle : https://support.google.com/googleplay/android-developer/answer/9899034).
- **Risque technique principal** : autorisation inter-tenant et entretien de N bases / secrets / connexions / migrations. Tests A/B et restauration obligatoires, aucune assurance possible avant implémentation.
- **Contrat API OpenAPI initial non exhaustif** : pas encore suffisant pour implémenter le parcours administratif et les parcours d'identité sans détailler d'autres routes.
- **Statut global** : utilisable comme base de discussion ; **G0 cadrage final en attente des arbitrages**, G1 non commencé ; production non autorisée.

## Points contrôlés et cohérents sur le papier
- Une commande / un panier ne traversent jamais plusieurs tenants.
- Les privilèges de base SQL et la résolution tenant se font côté serveur.
- Pas de DB tenant connection string dans une application mobile.
- Pas de tarif client autoritatif ; snapshot transactionnel de commande.
- Outbox locale + consommateur idempotent pour projection marketplace future.
- Kotlin assure réseau/cache/sécurité locale ; React ne sert que de présentation.
- Publication de nouvelles apps ne remplace pas les anciennes ; contrats rétrocompatibles.
- API et backoff/idempotence envisagés pour pertes de réseau.

## Règles de résolution
**Fixé sans arbitrage** : secrets panier ; endpoint de zones ; protection transport ; intégrité checkout ; tests d'isolation ; contrats versionnés ; sauvegarde vérifiée.

**Arbitrage du porteur de projet** : modèle de paiement, vente/territoires/devise, distribution/signature, offre commerciale, expérience client, politique SAV, importance des notifications, visibilité/licence et budget.

**Choix délégué à l'équipe technique** : librairies UI, gestion d'état, structure modules, limites de pools, méthodes de monitoring ; décision par ADR et tests, sans promesses de performances chiffrées avant mesures.

## Gates
- **G0** : arbitrages consignés, contradictions levées, contrat révisé, revu.
- **G1** : registre + 2 bases réelles, auth complète, CI typecheck/test, isolations vérifiées, Android skeleton compile.
- **G2** : catalogue, panier, commandes et flux paiements manuels E2E.
- **G3** : Android et console fonctionnels, pipeline de deux marques.
- **G4** : aspects légaux, distribution, paiement éventuel, backup/restauration, test de sécurité et monitoring.
- **G5** : industrialisation sans régression d'anciennes applications.
